第 1 课 · 可维护代码的第一把尺子

单一事实来源

你这份代码已经做对了大半。这一课，补上那最后一块——用一个原则解释你所有的"不足"。

先定义"可维护"到底指什么

可维护 ≠ 注释多、文件多、代码整齐。它只有一个硬指标：改一个东西，要不要同时记住改好几个地方？

如果答案是"要"，那迟早有一天你会漏改其中一处，然后出现"首页说的和帮助中心说的不一样"这种 bug——不是不会写代码，是同一份事实被复制到了多个地方。

原则单一事实来源（Single Source of Truth）：一个"事实"——一个数字、一段文案、一条颜色、一个尺寸——只在代码里出现一次。要改，只改那一处，别处引用它，自动生效[2]。

你代码里已经做对的部分（先给肯定）

  • 下载链接集中在 src/constants/download.js —— iOS 上架后只改一处，全站生效 ✅
  • 复用的图片路径集中在 src/data/images.js ✅
  • 所有颜色/圆角/字号收敛成 CSS 变量（tokens.css）✅

你已经会用这把尺子了。下面三个反例是它没扫到的角落。

反例 1 · 一个元素的样式住在三个地方

打开 src/components/sections/PricingInline.vue：卡片背景、圆角、阴影、渐变全部写成了模板里的内联样式对象，还硬编码了 #000、#059669 这些色值：

<article :style="cardStyle(plan)"> ... </article>
<span :style="{ fontSize: 'clamp(50px, 4vw, 66px)', color: '#000' }">...</span>

与此同时 src/styles/sections/pricing.css 里，又有一套全局样式——为了压过内联样式，甚至动用了 !important：

.price-grid-inline { align-items: stretch !important; }
/* 小屏又要覆盖回内联 grid，还是 !important */

同一个区块，样式散在"模板字符串"和"CSS 文件"两个世界，还互相打架。颜色写在 tokens.css 一遍、内联又写一遍——改主题时必然漏改。这套颜色、这些规则，没有单一来源。

这还正好撞上官方风格指南 Priority C 的建议：多种做法都可行时，"选一种，保持一致"[1]。三套并行，等于没选。

反例 2 · 同一段 FAQ 文案出现在两个文件

首页的"常见问题"读的是 src/data/faq.js（结构化数组）；帮助中心读的是 src/data/legal/help.js（HTML 字符串）。两者讲的是同一批问题：

// faq.js —— 首页
{ q: 'AI怎么算出我该吃多少？', a: '...' }

// help.js —— 帮助中心（同一句话，换了个说法存成 HTML）
<summary>AI 怎么算出我该吃多少？</summary>

改一遍配送范围，要记得改两处。漏一处，两个页面就自相矛盾。这份文案，没有单一来源。

反例 3 · README 描述的技术栈，和 package.json 不是一回事

README.md 写着"Pinia 3、Supabase JS、Element Plus、SCSS、stores/、utils/"。但 package.json 的依赖只有 vue 和 vue-router，仓库里也没有 stores/、utils/ 目录。[1]

文档是一份"事实"，代码是另一份"事实"。哪天你照着 README 装东西、找文件，就会被带到沟里。

怎么识别：三问

  1. 它出现了几次？搜一下，两次以上就是危险信号。
  2. 改它，我要记得去改几个文件？需要"同时记住多处"的，迟早漏。
  3. 这些地方各写各的，会不会不一致？用 !important 打架、措辞对不上 = 已发病。

三问里任一处亮红灯，就是违反单一事实来源。下一步不是急着重构，而是先把它记进清单——这课就是教你把尺子磨利。

自测

1. 判断代码是否可维护，最关键的一条是？

2. PricingInline 的卡片样式写在哪？

3. 同一段 FAQ 文案出现两处，要改文案时？

动手练习（约 10 分钟）

  1. 打开 src/components/sections/PricingInline.vue，数一数模板里出现了多少个 :style。找一处你最想改的（比如写死了颜色或尺寸的），想想它该住在哪个文件、用哪个 token。
  2. 打开 README.md 的"技术栈"小节和 package.json，找出至少 1 处不一致。
  3. 用"三问"扫一眼 src/data/，再找出 1 个新的重复数据源（提示：比较 faq.js 和 legal/help.js）。

做完把答案发我，我们核对，再决定下一课动哪个刀。
