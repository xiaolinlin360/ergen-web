三问识别"单一事实来源"被破坏

对代码里任何一个"东西"（一个数字、一段文案、一条颜色、一个尺寸、一条规则）问三句话：

  1. 它出现了几次？搜索一下，两次以上就是危险信号。
  2. 改它要记得去改几个文件？需要"同时记住多处"的地方，迟早漏改。
  3. 这些地方各写各的，会不会不一致？用 !important 打架、两处文案措辞不同 = 已发病。
核心一个"事实"只在代码里出现一次。要改，只改那一处，别处自动生效。

优先修什么（性价比排序）

  1. 会"改一处漏一处"的重复数据源 —— 最容易被你本人踩坑。
  2. 内联样式里写死的颜色/尺寸 —— 绕过 token，改主题时漏网。
  3. README 与现实的漂移 —— 新人/未来的你都会被带偏。
  4. 没有自动化护栏 —— 重构全靠手感。

词汇表

单一事实来源（Single Source of Truth）：
一个事实只定义一次，其它地方引用它。改这一处，处处生效。
避免：多处硬编码、重复数据源

内联样式（inline style）：
写在模板标签上的 :style="{...}"。无法用伪类/媒体查询，难以复用，且会把规则拆散到各处。
避免：把布局/颜色/尺寸写成内联对象

Design Token（设计令牌）：
集中定义的 CSS 变量（如 --mint、--r-2xl）。全站只改一处即可换主题。
在本仓库：src/styles/tokens.css

Scoped CSS：
SFC 里 <style scoped> 的样式只作用于本组件。反模式是"全局类名全靠约定不报错"。
本仓库现状：全局 section CSS + 少量 scoped + 大量内联，三套并行

Composable：
把可复用逻辑抽成函数（如 useInView），一个逻辑只写一次。
避免：每个组件各写一份 IntersectionObserver

!important：
强制覆盖其它规则。一旦用得多，就说明样式在互相打架（通常是内联样式 vs CSS 文件）。
避免：用它来"镇压"内联样式

自动化护栏（guardrails）：
lint、类型检查、构建检查、测试。让"改坏了"在提交前被抓住，而不是上线后才发现。
本仓库现状：无 ESLint、无类型检查、无测试

脚手架残留（scaffolding leftovers）：
初始化模板留下的死代码（如 assets/main.scss 只剩一条被覆盖的 body 规则），及随之而来的无用依赖。
避免：为"也许以后用得上"保留死代码

本清单配套第 1 课：单一事实来源：一个东西，只在一个地方定义。对任何术语有疑问，直接问我。
